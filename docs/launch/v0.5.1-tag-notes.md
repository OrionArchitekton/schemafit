## Steps (for Dan)

Tagging is the publish gate: a `v*` tag triggers `.github/workflows/release.yml`,
which publishes to PyPI (Trusted Publishing) and pushes the GHCR image. A PyPI
version cannot be re-uploaded, so the tagged commit must already be final.
The workflow does not create the GitHub Release; step 4 does that.

1. **Before merging PR #10**, date the changelog on the PR branch so the tagged
   commit carries it (main requires a PR, so this cannot happen after merge):

   ```bash
   git checkout fix/launch-readme && git pull --ff-only
   sed -i 's/^## \[0.5.1\] - Unreleased/## [0.5.1] - YYYY-MM-DD/' CHANGELOG.md   # real date
   git commit -am "chore: date 0.5.1 changelog" && git push
   ```

2. Merge PR #10, then tag main:

   ```bash
   git checkout main && git pull --ff-only
   grep -q '^## \[0.5.1\] - 20' CHANGELOG.md || { echo "changelog not dated"; exit 1; }
   python -m pytest && ruff check .
   git tag -a v0.5.1 -m "schemafit v0.5.1"
   git push origin v0.5.1
   ```

3. Wait for both publish jobs to succeed before announcing anything. The loop
   waits for the run on the tag's own commit, so it cannot pick up an older
   release run:

   ```bash
   SHA=$(git rev-list -n1 v0.5.1)
   RUN=""
   until [ -n "$RUN" ]; do
     sleep 5
     RUN=$(gh run list --workflow release.yml --commit "$SHA" --event push --json databaseId --jq '.[0].databaseId // empty')
   done
   gh run watch --exit-status "$RUN"
   ```

4. Create the GitHub Release from the body file:

   ```bash
   gh release create v0.5.1 --verify-tag \
     --title "schemafit v0.5.1: README refresh and plain-text status separator" \
     --notes-file docs/launch/v0.5.1-release-body.md
   ```

5. Check: `pip index versions schemafit` lists 0.5.1, and running the README demo
   block prints exactly the transcript under it.
